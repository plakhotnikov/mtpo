## 1. Введение

Данная работа является продолжением практической работы № 1, в которой было реализовано консольное Java-приложение для решения NP-полной задачи Subset Sum двумя алгоритмами динамического программирования на разных структурах данных.

**Почему BDD — эволюция TDD.** В статье "Introducing BDD" [1] Дэн Норт описывает три проблемы, с которыми сталкиваются разработчики при освоении TDD:

1. **Непонятно, с чего начинать** — разработчик не знает, какой тест писать первым. BDD предлагает начинать с поведения: формулировка "should" (должен) вместо "test" переключает мышление с тестирования внутренней реализации на описание ожидаемого поведения системы.

2. **Непонятно, что тестировать, а что — нет.** Норт предлагает формулировать имена тестов как предложения на естественном языке ("should return zero when balance is empty"), что автоматически ограничивает область тестирования — если предложение невозможно сформулировать осмысленно, тест не нужен.

3. **Непонятно, что считать удачным тестом.** BDD вводит единый шаблон сценариев: **Given** (начальное состояние) — **When** (действие) — **Then** (ожидаемый результат). Этот шаблон стал основой языка Gherkin, позволяющего описывать поведение системы на языке, понятном всем участникам проекта.

Gherkin — язык описания поведения, получивший название "Маринованный огурец". Его основной синтаксис:

- **Feature** — группа связанных сценариев с описанием пользовательской истории (As a / I want / So that);
- **Scenario** / **Scenario Outline** — конкретный сценарий поведения; Outline позволяет параметризовать через таблицу Examples;
- **Given / When / Then** — три основных шага: предусловие, действие, ожидаемый результат;
- **And / But** — дополнительные шаги для улучшения читаемости; But подчёркивает контраст с предыдущим утверждением;
- **Background** — общие шаги для всех сценариев внутри Feature или Rule;
- **Rule** — группировка сценариев по бизнес-правилу;
- **DataTable** — табличные данные, передаваемые непосредственно в шаг;
- **DocString** (тройные кавычки `"""`) — многострочные данные (JSON, XML и пр.);
- **Tags** (`@tag`) — метки для фильтрации запуска сценариев.

## 2. Описание плана BDD-тестирования

### 2.1. Основы Gherkin

Gherkin-файлы (`*.feature`) описывают поведение системы в формате, близком к естественному языку. Каждый файл начинается с ключевого слова `Feature:`, за которым следует пользовательская история. Сценарии внутри feature описывают конкретные примеры поведения через шаги Given/When/Then.

Ключевые элементы синтаксиса, использованные в проекте:

| Элемент | Описание | Где используется |
|---------|----------|------------------|
| Feature + User Story | Описание функциональности с указанием актора и выгоды | Все 6 feature-файлов |
| Background | Общие предусловия для всех сценариев | `array_solver.feature`, `hashmap_solver.feature`, `console_menu.feature` |
| Rule | Группировка сценариев по бизнес-правилу | `array_solver.feature` (2 правила), `solver_comparison.feature` (2 правила), `solver_heavy_load.feature` (3 правила) |
| Scenario Outline + Examples | Параметризованные сценарии | `array_solver.feature`, `hashmap_solver.feature`, `solver_comparison.feature`, `solver_heavy_load.feature` |
| Given / When / Then | Основные шаги | Все файлы |
| And | Дополнительные условия/проверки | Все файлы |
| But | Контрастное утверждение | `array_solver.feature` — "But the found subset size is less than 5" |
| DataTable | Входная таблица с данными | `hashmap_solver.feature` — таблица из 5 строк |
| DocString | Многострочный JSON | `json_io.feature` — два сценария с JSON-данными |
| Tags | Метки для фильтрации | `@heavy` (нагрузочные тесты), `@business-idea` (бизнес-идея) |
| Императивный стиль | Пошаговое взаимодействие | `console_menu.feature` — "Manual data input via console" |
| Декларативный стиль | Описание результата | `console_menu.feature` — "Solving a problem with both algorithm results displayed" |

### 2.2. Выбор фреймворка

Для реализации BDD-тестов выбран **Cucumber 7.15.0** для Java — наиболее зрелый и широко используемый BDD-фреймворк для JVM-платформы. Интеграция с JUnit 5 осуществляется через `cucumber-junit-platform-engine`.

Конфигурация в `pom.xml`:

```java
@Suite
@IncludeEngines("cucumber")
@SelectClasspathResource("com/subsetsum/bdd")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.subsetsum.bdd")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME,
    value = "pretty, html:target/cucumber-reports/cucumber.html, json:target/cucumber-reports/cucumber.json")

```

Тяжёлые тесты вынесены в отдельный Maven-профиль `heavy`:

```bash

mvn test            # Обычные тесты (not @heavy) — фильтрация в junit-platform.properties
```

### 2.3. Описание тестовых случаев и BDD-тестов

Реализовано **6 feature-файлов** с **39 сценариями** (из них 14 помечены тегом `@heavy`).

#### Feature 1: `array_solver.feature` — ArrayDP-алгоритм (11 сценариев)

Пользовательская история: пользователь хочет решать задачу Subset Sum табличным DP-алгоритмом на `boolean[][]` для быстрого нахождения подмножества с заданной суммой для неотрицательных чисел.

Демонстрируемые элементы: **Background** (выбор солвера ArrayDP), **Rule** (2 штуки: корректный поиск + валидация), **Scenario Outline** (5 вариантов), **But** ("But the found subset size is less than 5" — подмножество найдено, но оно не совпадает со всем входным набором).

```gherkin
  Rule: Correctly finding subsets for non-negative numbers

    Scenario: Finding a subset in a simple set
      Given the input numbers are "3, 7, 1, 8, 2"
      And the target sum is 11
      When the solver runs
      Then the result should be "found"
      And the subset sum equals 11
      But the found subset size is less than 5
```

#### Feature 2: `hashmap_solver.feature` — HashMapDP-алгоритм (8 сценариев)

Пользовательская история: пользователь хочет решать задачу Subset Sum с помощью HashMap-алгоритма, поддерживающего отрицательные числа.

Демонстрируемые элементы: **Background**, **Rule**, **DataTable** (таблица из 5 строк с разными наборами данных), **Scenario Outline** с отрицательными числами.

```gherkin
  Scenario: Data table with expected results
    When the solver is run for each row of the table:
      | numbers            | targetSum | expected  |
      | 1, 2, 3            | 6         | found     |
      | -1, -2, -3         | -3        | found     |
      | 5, 10, 15          | 7         | not found |
      | -5, 10, -3, 8      | 2         | found     |
      | 100, 200, 300      | 50        | not found |
    Then all table results match expectations
```

#### Feature 3: `json_io.feature` — JSON ввод/вывод (4 сценария)

Пользовательская история: пользователь хочет загружать данные из JSON-файла и сохранять результаты для автоматизации пакетной обработки.

Демонстрируемые элементы: **DocString** (многострочные JSON-данные в тройных кавычках), полный цикл чтение → решение → запись.

```gherkin
  Scenario: Successfully reading input data from a JSON file
    Given a JSON file exists with content:
      """
      {
        "numbers": [1, 2, 3, 4, 5],
        "targetSum": 9
      }
      """
    When the file is read via JsonFileReader
    Then the input data contains numbers "1, 2, 3, 4, 5"
    And the input target sum equals 9
```

#### Feature 4: `console_menu.feature` — Консольное меню (4 сценария), тег `@business-idea`

Пользовательская история: студент, изучающий алгоритмы, хочет удобный интерфейс для ввода данных и визуального сравнения двух алгоритмов решения NP-полной задачи.

Демонстрируемые элементы: **тег `@business-idea`** (обобщение бизнес-идеи), **императивный стиль** (пошаговое взаимодействие с меню), **декларативный стиль** (описание желаемого результата одним шагом).

Императивный стиль — каждый шаг пользовательского взаимодействия описан явно:
```gherkin
  Scenario: Manual data input via console (imperative style)
    When the user selects menu option "1"
    And the user enters numbers "5 10 15 20"
    And the user enters target sum "25"
    And the user declines to save the result
    Then the output contains "Результат"
```

Декларативный стиль — одно действие описывает весь результат:
```gherkin
  Scenario: Solving a problem with both algorithm results displayed (declarative style)
    When the user solves a problem with numbers "5 10 15 20" and sum "25"
    Then both algorithm results are displayed
    And both algorithms find a solution
```

#### Feature 5: `solver_comparison.feature` — Сравнение алгоритмов (12 сценариев)

Пользовательская история: исследователь алгоритмов хочет сравнить время выполнения ArrayDP и HashMapDP на различных наборах данных для выявления зависимостей производительности от размера и характеристик входных данных.

Демонстрируемые элементы: **Rule** (2 штуки: корректность + нагрузка), **Scenario Outline** с пятью размерами (20, 50, 100, 200, 500), генерация датасетов, замер времени и памяти.

#### Feature 6: `solver_heavy_load.feature` — Тяжёлые нагрузочные тесты (14 сценариев), тег `@heavy`

Пользовательская история: исследователь хочет запускать тяжёлые нагрузочные тесты с детальным профилированием для определения максимальных границ производительности.

Три правила (Rule):
1. **Предварительный эксперимент** — 9 наборов данных (Scenario Outline) для нахождения границы t₁;
2. **Полный план нагрузки** — 2 типа × 2 размера (средний + максимальный): DENSE_MED_1000, DENSE_MAX_60000, SPARSE_MED_1000, SPARSE_MAX_25000;
3. **Сравнение BDD vs unit-тест** — один набор данных 500 элементов, аналогичный SolverComparisonTest.

### 3.2. Алгоритмы генерации наборов данных

Генерация реализована в классе `ComparisonSteps.java`, метод `aGeneratedDataset()`:

```java
@Given("a generated dataset {string} of {int} non-negative numbers in range [{int}, {int}]")
public void aGeneratedDataset(String name, int size, int min, int max) {
    Random random = new Random(42); // фиксированный seed для воспроизводимости
    List<Integer> numbers = new ArrayList<>();
    for (int i = 0; i < size; i++) {
        numbers.add(min + random.nextInt(max - min + 1));
    }
    int totalSum = numbers.stream().mapToInt(Integer::intValue).sum();
    int targetSum = totalSum / 2; // целевая сумма = половина общей суммы
    // ...
}
```

Ключевые характеристики генерации:
- **Seed = 42** — фиксированный для воспроизводимости результатов;
- **targetSum = totalSum / 2** — обеспечивает нетривиальный, но разрешимый экземпляр задачи (задача о разбиении);
- Два типа данных, определяемые диапазоном значений:
  - **Dense** (плотные): числа в диапазоне [1, 100] — малый разброс значений → малая целевая сумма → компактная DP-таблица для ArrayDP;
  - **Sparse** (разреженные): числа в диапазоне [1, 500..1000] — большой разброс → большая целевая сумма → разросшаяся DP-таблица.

Сгенерированные данные сохраняются в папку `target/datasets/` в формате JSON.

### 3.3. Предварительный эксперимент

Цель предварительного эксперимента — найти размеры наборов данных, при которых время решения достигает t₁ ∈ [2–10] минут.

Предварительный эксперимент реализован в `solver_heavy_load.feature`, Rule 1. Замеряется время обоих алгоритмов на наборах возрастающего размера:

| Датасет | n | Диапазон | target (≈) | n × target | Ожидаемое поведение |
|---------|---|----------|-----------|-----------|-------------------|
| PRELIM_DENSE_500 | 500 | [1,100] | 25 250 | 12.6 M | Быстро |
| PRELIM_DENSE_1000 | 1 000 | [1,100] | 50 500 | 50.5 M | Быстро |
| PRELIM_DENSE_2000 | 2 000 | [1,100] | 101 000 | 202 M | Секунды |
| PRELIM_DENSE_3000 | 3 000 | [1,100] | 151 500 | 454.5 M | Секунды |
| PRELIM_DENSE_5000 | 5 000 | [1,100] | 252 500 | 1.26 G | Десятки секунд |
| PRELIM_SPARSE_500 | 500 | [1,1000] | 250 250 | 125 M | Секунды |
| PRELIM_SPARSE_1000 | 1 000 | [1,1000] | 500 500 | 500.5 M | Секунды |
| PRELIM_SPARSE_2000 | 2 000 | [1,1000] | 1 001 000 | 2 G | Десятки секунд |
| PRELIM_SPARSE_3000 | 3 000 | [1,1000] | 1 501 500 | 4.5 G | Минуты |

Здесь target ≈ n × avg / 2, где avg = (min + max) / 2 — среднее значение элемента.

**Экстраполяция для определения максимальных размеров.**

Оба алгоритма имеют сложность O(n × target). Поскольку target ∝ n (target = totalSum / 2 ≈ n × avg / 2), время растёт как O(n²). Это позволяет экстраполировать по формуле:

> T(n₂) ≈ T(n₁) × (n₂ / n₁)²

**Dense (диапазон [1, 100], avg ≈ 50.5):**

Из обычного прогона (`solver_comparison.feature`) известно: LOAD_DENSE_1000 → HashMapDP ≈ 67 мс при n = 1000.

Для достижения t₁ = 120 000 мс (2 минуты):
- n₂ = n₁ × √(T₂ / T₁) = 1000 × √(120 000 / 67) ≈ 1000 × 42.3 ≈ **42 300**

Но это для HashMapDP. Также нужно учесть ограничение ArrayDP по памяти:
- Таблица `boolean[n+1][target+1]`, target ≈ 50.5 × n / 2 = 25.25n
- При n = 60 000: размер = 60 001 × 1 515 001 ≈ **90.9 ГБ** → OOM даже при `-Xmx8g`
- При n = 42 000: размер = 42 001 × 1 060 501 ≈ **44.5 ГБ** → тоже OOM

Таким образом, для dense данных ArrayDP гарантированно получит OOM при любом n, дающем t₁ ≥ 2 мин. Выбрано **n = 60 000** — при котором HashMapDP работает достаточно долго (экстраполяция: ~120–180 с), а ArrayDP демонстрирует ограничение по памяти.

**Sparse (диапазон [1, 500], avg ≈ 250.5 для SPARSE_MAX; [1, 1000] для PRELIM):**

Из обычного прогона: LOAD_SPARSE_1000 → HashMapDP ≈ 4 875 мс при n = 1000, max = 10 000.

Для SPARSE_MAX используется диапазон [1, 500] (avg ≈ 250.5), что даёт target ≈ 125.25n. Пересчёт:
- При n = 1000, max = 500: target ≈ 125 250, n × target ≈ 125 M
- При n = 25 000, max = 500: target ≈ 3 131 250, n × target ≈ 78.3 G
- Отношение: 78.3G / 125M = 626 → T ≈ 67 мс × 626 ≈ **42 с** (по dense baseline)

Или по sparse baseline (n=1000, max=1000, T≈4875 мс, n×target ≈ 500.5G):
- n = 25 000, max = 500: n×target = 78.3G — меньше, чем baseline, но n больше → аналогичная ситуация с OOM для ArrayDP

Выбрано **n = 25 000** с диапазоном [1, 500] — экстраполяция даёт время HashMapDP ≈ 2–3 минуты, ArrayDP получает OOM.

**Итого — план полного эксперимента (2 типа × 2 размера):**

| Датасет | n | Диапазон | Тип | Обоснование |
|---------|---|----------|-----|-------------|
| DENSE_MED_1000 | 1 000 | [1, 100] | Dense средний | Оба алгоритма справляются за секунды |
| DENSE_MAX_60000 | 60 000 | [1, 100] | Dense максимальный | HashMapDP: ~2–3 мин, ArrayDP: OOM |
| SPARSE_MED_1000 | 1 000 | [1, 1000] | Sparse средний | Оба алгоритма справляются за секунды |
| SPARSE_MAX_25000 | 25 000 | [1, 500] | Sparse максимальный | HashMapDP: ~2–3 мин, ArrayDP: OOM |

### 3.5. Профилирование

Профилирование реализовано в двух классах:

**ComparisonSteps** (`solver_comparison.feature`) — измеряет время и память на уровне вызова `solver.solve()`, использует встроенные метрики `SubsetSumResult.getExecutionTimeMs()` и `getMemoryUsedBytes()`.

**HeavyLoadSteps** (`solver_heavy_load.feature`) — полный пайплайн профилирования:

1. **Генерация данных** — `System.nanoTime()` вокруг генерации (в ComparisonSteps);
2. **Сохранение в JSON** — `System.nanoTime()` вокруг записи файла;
3. **Загрузка из JSON** — `System.nanoTime()` вокруг чтения файла + верификация;
4. **Решение ArrayDP** — `System.gc()` + `System.nanoTime()`, с OOM-защитой через `try { ... } catch (OutOfMemoryError)` для максимальных наборов;
5. **Решение HashMapDP** — `System.gc()` + `System.nanoTime()`.

Результаты записываются в `target/datasets/heavy_load_report.txt` и выводятся в stdout.

OOM-защита необходима потому, что ArrayDP выделяет таблицу `boolean[n+1][target+1]`. Для DENSE_MAX_60000 при target ≈ 3 000 000 размер таблицы составляет ≈ 180 ГБ, что невозможно разместить даже при `-Xmx8g`. HashMapDP хранит только достижимые суммы и не имеет этого ограничения.

## 5. Заключение

### Соответствие теоретической сложности экспериментальным данным

Оба алгоритма имеют теоретическую сложность O(n × target) в худшем случае. Эксперименты подтверждают это:
- Для SCALE_POS: при увеличении n с 20 до 500 (в 25 раз) и пропорциональном росте target, время ArrayDP выросло с 0.06 мс до 36 мс (~600 раз), что соответствует квадратичному росту произведения n × target;
- Для LOAD_SPARSE_1000 (target = 2 426 810) время резко возрастает до 3.7 с — высокий target даёт огромную таблицу;
- Для максимальных наборов (DENSE_MAX_60000) ArrayDP выходит за пределы 8 ГБ памяти (OOM), что также подтверждает пространственную сложность O(n × target).

### Выводы из сравнения распределений

- **ArrayDP быстрее HashMapDP** на всех протестированных размерах при плотных данных (ratio 0.3–0.8x);
- **HashMapDP эффективнее по памяти** на разреженных данных: 646 МБ vs 4.2 ГБ для LOAD_SPARSE_1000;
- **ArrayDP имеет жёсткое ограничение по памяти**: при n × target > ~2 ГБ (для boolean[][]) алгоритм получает OutOfMemoryError, в то время как HashMapDP продолжает работать;
- Выбор алгоритма зависит от характеристик данных: ArrayDP оптимален для плотных данных с небольшим target, HashMapDP — для разреженных данных, отрицательных чисел и больших target.

### Выводы о сравнении BDD и модульных тестов

В проекте реализованы оба вида тестов:
- **Unit-тесты** (JUnit 5): 130 тестов в 8 классах, включая `SolverComparisonTest` с 11 параметризованными случаями;
- **BDD-тесты** (Cucumber): 39 сценариев (70 запусков с учётом Scenario Outline) в 6 feature-файлах + 14 сценариев в @heavy.

Сравнение по критериям:

| Критерий | Unit-тесты | BDD-тесты |
|----------|-----------|-----------|
| Читаемость | Требуют знания Java | Gherkin понятен без программирования |
| Быстродействие | Минимальный overhead | Overhead на парсинг Gherkin, поиск step definitions |
| Гранулярность | Один метод / ветвь | Сценарий = бизнес-поведение |
| Переиспользование | Через наследование / утилиты | Через общие шаги (steps) между feature-файлами |
| Поддержка нагрузочных тестов | Нативно (прямой вызов) | Через step definitions + TestContext |
| Время прогона (весь набор) | ~1 с (130 unit-тестов) | ~8.5 с (70 BDD-сценариев, без @heavy) |

BDD-тесты добавляют overhead: парсинг feature-файлов, маршрутизация шагов через регулярные выражения, создание step-классов через Cucumber DI. На идентичных данных (BDD_VS_UNIT_500 vs SolverComparisonTest) время самих вычислений одинаково, но общий прогон BDD-сьюта занимает больше за счёт инфраструктуры.

Главное преимущество BDD — мост между требованиями и кодом: feature-файлы служат одновременно спецификацией поведения и автотестом.
