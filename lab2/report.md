## Введение

Данная работа является продолжением практической работы №1, в которой было разработано консольное Java-приложение для решения NP-полной задачи Subset Sum двумя алгоритмами динамического программирования (ArrayDP на `boolean[][]` и HashMapDP на `HashMap<Integer, Integer>`). Приложение было покрыто 128 модульными тестами с использованием JUnit 5, Mockito и Hamcrest.

В рамках текущей работы необходимо приобрести навыки по разработке через тестирование поведения (Behavior-Driven Development, BDD). Основные задачи:
- изучение подхода BDD и синтаксиса Gherkin;
- выбор и освоение фреймворка Cucumber для Java;
- составление Gherkin-историй (feature-файлов) для модулей приложения;
- проведение нагрузочного тестирования с профилированием двух алгоритмов;
- сравнение BDD-тестов с модульными тестами.

### Почему BDD — эволюция TDD

Дэн Норт в статье "Introducing BDD" описывает проблемы, с которыми сталкиваются разработчики при использовании TDD:
1. **Неясность, что именно тестировать** — разработчики не знают, с чего начать, что тестировать, а что нет, и как именно называть тесты.
2. **Разрыв между бизнес-требованиями и кодом** — модульные тесты проверяют техническую корректность, но не гарантируют соответствие бизнес-целям.
3. **Тесты сложно читать непрограммистам** — названия тестов вроде `testArrayBoundsCheck` не несут бизнес-смысла.

BDD решает эти проблемы, предлагая:
- описывать поведение системы на **естественном языке** в формате пользовательских историй;
- использовать шаблон **Given-When-Then** (Дано-Когда-Тогда) для структурирования сценариев;
- сделать тесты **исполняемой документацией**, понятной всем участникам проекта.

## Описание плана BDD-тестирования

### Основы Gherkin

Gherkin — это язык описания поведения системы, используемый в BDD-фреймворках. Основные элементы:

| Ключевое слово | Назначение | Пример |
|---|---|---|
| **Feature** | Описание группы сценариев с пользовательской историей | `Feature: Solving Subset Sum with ArrayDP` |
| **Background** | Общие предусловия для всех сценариев | `Background: Given the solver is "ArrayDP"` |
| **Scenario** | Конкретный тестовый случай | `Scenario: Finding a subset in a simple set` |
| **Scenario Outline** | Параметризованный сценарий | С таблицей `Examples:` |
| **Rule** | Группировка сценариев по бизнес-правилу | `Rule: Input data validation` |
| **Given** | Начальные условия (предусловия) | `Given the input numbers are "1, 2, 3"` |
| **When** | Действие пользователя | `When the solver runs` |
| **Then** | Ожидаемый результат | `Then the result should be "found"` |
| **And** | Дополнительное условие/действие/результат | `And the subset sum equals 11` |
| **But** | Контрастное/противоречащее условие | `But the found subset size is less than 5` |
| **Examples** | Таблица данных для Scenario Outline | Таблица с `\|` разделителями |
| **DataTable** | Входная таблица данных | Встроенная таблица в шаге |

### Выбор фреймворка

Для реализации BDD-тестов выбран фреймворк **Cucumber 7.15.0** для Java. Обоснование:
- Cucumber — стандартный BDD-фреймворк для Java;
- тесная интеграция с JUnit 5 через `cucumber-junit-platform-engine`;
- генерация HTML и JSON отчётов;
- поддержка параметризации, таблиц данных, тегов и хуков.

### Описание тестовых случаев и BDD-тестов

Разработано **6 feature-файлов**:
- 5 основных (70 сценариев, запускаются по умолчанию);
- 1 тяжёлый нагрузочный с тегом `@heavy` (28 сценариев, отдельный профиль).

#### Feature 1: `array_solver.feature` — ArrayDP-солвер (11 сценариев)

**Пользовательская история**: As an application user, I want to solve the Subset Sum problem using a tabular DP algorithm on `boolean[][]`, so that I can quickly find a subset with a given sum for non-negative numbers.

Элементы:
- **Background**: инициализация алгоритма ArrayDP
- **Rule**: "Correctly finding subsets" (3 сценария) и "Input data validation" (2 сценария)
- **Scenario Outline** с таблицей `Examples` (5 вариаций)
- **But**: контрастное утверждение «подмножество найдено, **но** его размер меньше размера входных данных» (т.е. не весь набор)
- Шаги: Given, When, Then, And, But

#### Feature 2: `hashmap_solver.feature` — HashMapDP-солвер (8 сценариев)

**Пользовательская история**: As an application user, I want to solve the Subset Sum problem using a HashMap-based DP algorithm, so that I can find subsets even when negative numbers are present.

Элементы:
- **Background**: инициализация алгоритма HashMapDP
- **Rule**: "Support for negative numbers"
- **DataTable** (входная таблица) — тестирование 5 наборов данных в одном шаге
- **Scenario Outline** с отрицательными числами

#### Feature 3: `json_io.feature` — JSON ввод/вывод (4 сценария)

**Пользовательская история**: As an application user, I want to load input data from a JSON file and save results, so that I can automate batch processing.

Элементы:
- Чтение из файла, запись в строку
- Полный цикл: чтение → решение → запись
- Обработка ошибок
- DocString (многострочные JSON-данные)

#### Feature 4: `console_menu.feature` — Консольное меню (4 сценария, @business-idea)

**Пользовательская история** (бизнес-идея): As a student studying algorithms, I want a convenient interface for entering data and viewing results, so that I can visually compare two algorithms for solving an NP-complete problem.

Элементы:
- Тег `@business-idea` (обобщение типа бизнес-идея)
- **Императивный стиль** — подробные шаги: выбор пункта меню → ввод чисел → ввод суммы → отказ от сохранения → проверка вывода
- **Декларативный стиль** — один шаг: `When the user solves a problem with numbers "5 10 15 20" and sum "25"` → проверка результата

#### Feature 5: `solver_comparison.feature` — Сравнение алгоритмов (12 сценариев)

**Пользовательская история**: As an algorithm researcher, I want to compare execution time of ArrayDP and HashMapDP, so that I can identify performance dependencies.

Элементы:
- **Rule**: "Both algorithms produce the same result" и "Load testing"
- Генерация датасетов разных размеров (10–1000 элементов)
- Замер времени и памяти
- Сравнение плотных и разреженных данных
- Соответствие unit-тесту `SolverComparisonTest` (те же проверки found/not-found)

#### Feature 6: `solver_heavy_load.feature` — Тяжёлое нагрузочное тестирование (28 сценариев, @heavy)

Элементы:
- Тег `@heavy` — исключён из `mvn test`, запускается через `mvn test -Pheavy` (JVM с `-Xmx8g`)
- Предварительный эксперимент (9 сценариев): размеры 500–5000, dense и sparse
- Полный план 2×2 (4 сценария): 2 типа данных × 2 размера (medium + maximum)
- Защита от OOM для ArrayDP на больших датасетах
- Детальное профилирование: генерация → сохранение JSON → загрузка JSON → решение

### Алгоритм генерации наборов данных

Генерация осуществляется в классе `ComparisonSteps` в методе `aGeneratedDataset`:

```java
Random random = new Random(42); // Fixed seed for reproducibility
List<Integer> numbers = new ArrayList<>();
for (int i = 0; i < size; i++) {
    numbers.add(min + random.nextInt(max - min + 1));
}
int targetSum = totalSum / 2; // Target sum — half of total (worst case for DP)
```

Параметры генерации:
- **Размер** (size) — количество элементов в наборе
- **Диапазон значений** [min, max] — влияет на плотность/разреженность
- **Seed** = 42 — воспроизводимость экспериментов
- **Целевая сумма** = половина суммы всех элементов (обеспечивает наихудший случай для DP — максимальное число достижимых сумм для проверки)

### Кодировка названий наборов данных

Формат: `<ТИП>_<ПЛОТНОСТЬ>_<РАЗМЕР>`, где:
- **PRELIM** — предварительный эксперимент, **DENSE/SPARSE** — основной план, **SCALE** — масштабирование
- **DENSE** — плотные данные (диапазон [1, 100]), **SPARSE** — разреженные (диапазон [1, 500–1000])
- **Число** — количество элементов

| Код набора | Размер | Диапазон | Описание |
|---|---|---|---|
| `PRELIM_DENSE_500..5000` | 500–5000 | [1, 100] | Предварительный эксперимент, плотные |
| `PRELIM_SPARSE_500..3000` | 500–3000 | [1, 1000] | Предварительный эксперимент, разреженные |
| `DENSE_MED_1000` | 1000 | [1, 100] | Плотные, средний размер |
| `DENSE_MAX_60000` | 60000 | [1, 100] | Плотные, максимальный (t1 ≈ 2.5 мин) |
| `SPARSE_MED_1000` | 1000 | [1, 1000] | Разреженные, средний размер |

Датасеты сохраняются в `target/datasets/` в формате JSON.

Цель: определить границу t1 ∈ [2-10] минут для обоих типов данных.

**Предварительные результаты (HashMapDP):**

| Набор | n | Target | ArrayDP (мс) | HashMapDP (мс) | Ratio |
|---|---|---|---|---|---|
| PRELIM_DENSE_500 | 500 | 12786 | 18.72 | 43.16 | 0.43x |
| PRELIM_DENSE_1000 | 1000 | 25560 | 43.08 | 76.17 | 0.57x |
| PRELIM_DENSE_2000 | 2000 | 51284 | 142.30 | 228.70 | 0.62x |
| PRELIM_DENSE_3000 | 3000 | 77587 | 282.88 | 451.94 | 0.63x |
| PRELIM_DENSE_5000 | 5000 | 128690 | 798.83 | 1196.06 | 0.67x |
| PRELIM_SPARSE_500 | 500 | 126086 | 42.73 | 144.82 | 0.30x |
| PRELIM_SPARSE_1000 | 1000 | 253310 | 160.03 | 444.61 | 0.36x |
| PRELIM_SPARSE_2000 | 2000 | 501934 | 675.08 | 1653.29 | 0.41x |
| PRELIM_SPARSE_3000 | 3000 | 748387 | 1980.39 | 3753.85 | 0.53x |

**Экстраполяция для нахождения t1:**
- HashMapDP Dense: при n=5000 → 1.2с. Рост ~O(n²). Для 120с: n ≈ 60000.
- HashMapDP Sparse: при n=3000 → 3.75с. Рост ~O(n^1.8). Для 120с: n ≈ 25000.

**Вывод предварительного эксперимента:** максимальные наборы установлены как DENSE_MAX_60000 и SPARSE_MAX_25000.

### Профилирование

Профилирование выполняется на 4 этапах пайплайна:

```
[1] Генерация данных → [2] Сохранение в JSON → [3] Загрузка из JSON → [4] Решение задачи
```

**Результаты полного плана 2×2:**

| Набор | n | Target | ArrayDP (мс) | HashMapDP (мс) | Save (мс) | Load (мс) |
|---|---|---|---|---|---|---|
| DENSE_MED_1000 | 1000 | 25560 | 19.04 | 47.81 | 0.15 | 1.05 |
| **DENSE_MAX_60000** | 60000 | 1520174 | **OOM** | **153,372** (2.56 мин) | 0.22 | — |
| SPARSE_MED_1000 | 1000 | 253310 | 154.62 | 436.61 | 0.15 | 0.65 |
| **SPARSE_MAX_25000** | 25000 | 3124645 | **OOM** | **139,083** (2.32 мин) | — | — |

Наблюдения:
- **Генерация и I/O** пренебрежимо малы (< 1 мс даже для 60000 элементов);
- **Решение задачи** доминирует в пайплайне (> 99.9% времени);
- **ArrayDP**: OOM при n ≥ 15000 (таблица `boolean[n][target]` не помещается в 8 ГБ);
- **HashMapDP**: работает при любых размерах, но в 2-3x медленнее ArrayDP на тех же данных.

## Анализ результатов экспериментов

### Зависимость времени от размера данных

**ArrayDP — O(n × targetSum):**

| n | Target | Время (мс) | n × target | Пропускная способность |
|---|---|---|---|---|
| 500 | 12786 | 18.72 | 6.4M | 342 M ops/s |
| 1000 | 25560 | 43.08 | 25.6M | 594 M ops/s |
| 2000 | 51284 | 142.30 | 102.6M | 721 M ops/s |
| 3000 | 77587 | 282.88 | 232.8M | 823 M ops/s |
| 5000 | 128690 | 798.83 | 643.5M | 806 M ops/s |

Пропускная способность стабилизируется на ~800 M ops/s, подтверждая линейную зависимость O(n × target).

**HashMapDP — O(n × |reachable sums|):**

| n (dense) | Время (мс) | n (sparse) | Время (мс) |
|---|---|---|---|
| 500 | 43 | 500 | 145 |
| 1000 | 76 | 1000 | 445 |
| 2000 | 229 | 2000 | 1653 |
| 3000 | 452 | 3000 | 3754 |
| 5000 | 1196 | — | — |

Рост сверхлинейный (~n^1.8 для sparse, ~n^1.6 для dense) из-за роста числа достижимых сумм.

### Влияние плотности данных

- **Плотные данные** (диапазон [1, 100]): целевая сумма мала (~n×50), количество достижимых сумм ограничено. ArrayDP строит компактную таблицу. HashMapDP работает медленнее из-за накладных расходов HashMap (boxing, hashing, GC), но не критично.

- **Разреженные данные** (диапазон [1, 500–1000]): целевая сумма велика (~n×250–500). ArrayDP создаёт огромную таблицу и при n > 5000 упирается в OOM. HashMapDP хранит только достижимые суммы, но их количество растёт быстрее, что замедляет работу.

### Сравнение ArrayDP и HashMapDP

| Критерий | ArrayDP | HashMapDP |
|---|---|---|
| Временная сложность | O(n × target) | O(n × \|reachable\|) |
| Пространственная сложность | O(n × target) | O(\|reachable\|) |
| Поддержка отрицательных | Нет | Да |
| Скорость (плотные) | Быстрее в 2-3x | Медленнее |
| Скорость (разреженные) | Быстрее в 2-3x (если хватает RAM) | Медленнее, но работает всегда |
| Максимальный размер (8 ГБ) | ~5000 (sparse) / ~10000 (dense) | 60000+ |
| Предсказуемость | O(n×target) — всегда | Зависит от данных |

## Заключение

### Соответствие теоретической оценки экспериментам

- **ArrayDP: O(n × targetSum)** — подтверждено. Пропускная способность стабильна на ~800 M ops/s. Узкое место — память: таблица `boolean[n][target]` при n=3000, target=750K занимает 2.5 ГБ.
- **HashMapDP: O(n × |reachable sums|)** — подтверждено. Рост сверхлинейный (~n^1.6–1.8) из-за увеличения числа достижимых сумм. На максимальных наборах (n=60000 dense, n=25000 sparse) время составило 2.3–2.6 минуты.

### Выводы из сравнения алгоритмов

ArrayDP стабильно быстрее HashMapDP в 1.5–3x на неотрицательных данных. Это объясняется:
- прямой индексацией массива (O(1) с cache-friendly доступом) vs. HashMap (O(1) амортизированно, но с overhead на хеширование, boxing Integer и GC);
- ArrayDP ограничен памятью и не поддерживает отрицательные числа;
- HashMapDP универсальнее и масштабируется на большие наборы данных.

### Сравнение BDD и модульных тестов

| Критерий | Модульные тесты (JUnit) | BDD-тесты (Cucumber) |
|---|---|---|
| Уровень абстракции | Код, методы, классы | Поведение, сценарии |
| Читаемость | Для разработчиков | Для всех участников проекта |
| Язык | Java | Gherkin (естественный язык) |
| Скорость (128/70 тестов) | ~10 сек | ~10 сек |
| Гранулярность | Отдельные методы и ветви | Бизнес-сценарии и потоки |
| Документирование | Косвенное (код) | Явное (feature-файлы) |
| Поддержка мокирования | Полная (Mockito) | Ограниченная |
| Параметризация | @CsvSource, @MethodSource | Scenario Outline, DataTable |
| Нагрузочное тестирование | Ручная настройка | Встроено в сценарии |
| Применимость | Техническая корректность | Бизнес-валидация |

Быстродействие: на одинаковых данных (BDD_VS_UNIT_500) BDD-тест через Cucumber даёт те же результаты, что unit-тест `SolverComparisonTest`. Накладные расходы Cucumber (~2 сек на инициализацию) заметны только при первом запуске.

**Итог**: BDD-тесты дополняют, а не заменяют модульные тесты. Unit-тесты обеспечивают глубокую техническую проверку (ветвления, моки), а BDD-тесты — валидацию на уровне бизнес-сценариев и исполняемую документацию.

### Запуск тестов

```bash
# Все тесты (unit + BDD, без @heavy)
mvn test

# Только BDD-тесты (без @heavy)
mvn test -Dtest=RunCucumberTest

# Тяжёлые нагрузочные тесты (@heavy, -Xmx8g)
mvn test -Pheavy

# Отчёт Cucumber → target/cucumber-reports/cucumber.html
# Отчёт нагрузки → target/datasets/heavy_load_report.txt
```
