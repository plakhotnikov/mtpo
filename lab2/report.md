## Введение

Данная работа является продолжением практической работы №1, в которой было разработано консольное Java-приложение для решения NP-полной задачи Subset Sum двумя алгоритмами динамического программирования (ArrayDP на `boolean[][]` и HashMapDP на `HashMap<Integer, Integer>`). Приложение было покрыто 128 модульными тестами с использованием JUnit 5, Mockito и Hamcrest.

В рамках текущей работы необходимо приобрести навыки по разработке через тестирование поведения (Behavior-Driven Development, BDD). Основные задачи:
- изучение подхода BDD и синтаксиса Gherkin;
- выбор и освоение фреймворка Cucumber для Java;
- составление Gherkin-историй (feature-файлов) для модулей приложения;
- проведение нагрузочного тестирования с профилированием двух алгоритмов;
- сравнение BDD-тестов с модульными тестами.

### Почему BDD — эволюция TDD

Дэн Норт в статье "Introducing BDD" описывает проблемы, с которыми сталкиваются разработчики при использовании TDD:
1. **Неясность, что именно тестировать** — разработчики не знают, с чего начать, что тестировать, а что нет, и как именно называть тесты.
2. **Разрыв между бизнес-требованиями и кодом** — модульные тесты проверяют техническую корректность, но не гарантируют соответствие бизнес-целям.
3. **Тесты сложно читать непрограммистам** — названия тестов вроде `testArrayBoundsCheck` не несут бизнес-смысла.

BDD решает эти проблемы, предлагая:
- описывать поведение системы на **естественном языке** в формате пользовательских историй;
- использовать шаблон **Given-When-Then** (Дано-Когда-Тогда) для структурирования сценариев;
- сделать тесты **исполняемой документацией**, понятной всем участникам проекта.

## Описание плана BDD-тестирования

### Основы Gherkin

Gherkin (Маринованный огурец) — это язык описания поведения системы, используемый в BDD-фреймворках. Основные элементы:

| Ключевое слово | Назначение | Пример |
|---|---|---|
| **Feature** | Описание группы сценариев с пользовательской историей | `Feature: Solving Subset Sum with ArrayDP` |
| **Background** | Общие предусловия для всех сценариев | `Background: Given the solver is "ArrayDP"` |
| **Scenario** | Конкретный тестовый случай | `Scenario: Finding a subset in a simple set` |
| **Scenario Outline** | Параметризованный сценарий | С таблицей `Examples:` |
| **Rule** | Группировка сценариев по бизнес-правилу | `Rule: Input data validation` |
| **Given** | Начальные условия (предусловия) | `Given the input numbers are "1, 2, 3"` |
| **When** | Действие пользователя | `When the solver runs` |
| **Then** | Ожидаемый результат | `Then the result should be "found"` |
| **And** | Дополнительное условие/действие/результат | `And the subset sum equals 11` |
| **But** | Отрицательное условие | `But the output does not contain "Ошибка"` |
| **Examples** | Таблица данных для Scenario Outline | Таблица с `\|` разделителями |
| **DataTable** | Входная таблица данных | Встроенная таблица в шаге |

Gherkin поддерживает локализацию на множество языков. В данном проекте используется английская версия Gherkin для читаемости Java-кода step definitions.

### Выбор фреймворка

Для реализации BDD-тестов выбран фреймворк **Cucumber 7.15.0** для Java. Обоснование:
- Cucumber — стандартный BDD-фреймворк для Java;
- тесная интеграция с JUnit 5 через `cucumber-junit-platform-engine`;
- поддержка русской локализации Gherkin;
- генерация HTML и JSON отчётов;

### Описание тестовых случаев и BDD-тестов

Разработано **5 feature-файлов** с общим количеством **70 сценариев**.

#### Feature 1: `array_solver.feature` — ArrayDP-солвер (11 сценариев)

**Пользовательская история**: Как пользователь приложения, я хочу решить задачу о сумме подмножества с использованием табличного DP-алгоритма на `boolean[][]`, чтобы быстро находить подмножество с заданной суммой для неотрицательных чисел.

Элементы:
- **Background**: инициализация алгоритма ArrayDP
- **Rule**: "Корректное нахождение подмножества" (3 сценария) и "Валидация входных данных" (2 сценария)
- **Scenario Outline** с таблицей `Примеры` (5 вариаций)
- Шаги: Given, When, Then, And

#### Feature 2: `hashmap_solver.feature` — HashMapDP-солвер (8 сценариев)

**Пользовательская история**: Как пользователь, я хочу решить задачу с использованием алгоритма на HashMap, чтобы находить подмножества даже при наличии отрицательных чисел.

Элементы:
- **Background**: инициализация алгоритма HashMapDP
- **Rule**: "Поддержка отрицательных чисел"
- **DataTable** (входная таблица) — тестирование 5 наборов данных в одном шаге
- **Scenario Outline** с отрицательными числами

#### Feature 3: `json_io.feature` — JSON ввод/вывод (4 сценария)

**Пользовательская история**: Как пользователь, я хочу загружать данные из JSON и сохранять результаты для автоматизации.

Элементы:
- Чтение из файла, запись в строку
- Полный цикл: чтение → решение → запись
- Обработка ошибок
- DocString (многострочные JSON-данные)

#### Feature 4: `console_menu.feature` — Консольное меню (4 сценария, @бизнес-идея)

**Пользовательская история** (бизнес-идея): Как студент, изучающий алгоритмы, я хочу иметь удобный интерфейс для ввода данных и просмотра результатов, чтобы наглядно сравнить работу двух алгоритмов решения NP-полной задачи.

Элементы:
- Тег `@business-idea` (обобщение типа бизнес-идея)
- **Императивный стиль** (подробные шаги взаимодействия с UI)
- **Декларативный стиль** (описание результата без деталей реализации)
- Ключевое слово **But**

#### Feature 5: `solver_comparison.feature` — Сравнение алгоритмов и нагрузочное тестирование (12 сценариев)

**Пользовательская история**: Как исследователь алгоритмов, я хочу сравнить время работы ArrayDP и HashMapDP, чтобы выявить зависимости производительности от размера и характеристик данных.

Элементы:
- **Rule**: "Оба алгоритма дают одинаковый результат" и "Нагрузочное тестирование"
- Генерация датасетов разных размеров (10–1000 элементов)
- Замер времени и памяти
- Сравнение плотных и разреженных данных
- **Scenario Outline** с 5 масштабными тестами

### Алгоритм генерации наборов данных

Генерация осуществляется в классе `ComparisonSteps` в методе `aGeneratedDataset`:

```java
Random random = new Random(42); // Fixed seed for reproducibility
List<Integer> numbers = new ArrayList<>();
for (int i = 0; i < size; i++) {
    numbers.add(min + random.nextInt(max - min + 1));
}
int targetSum = totalSum / 2; // Target sum — half of total
```

Параметры генерации:
- **Размер** (size) — количество элементов в наборе
- **Диапазон значений** [min, max] — влияет на плотность/разреженность
- **Seed** = 42 — воспроизводимость экспериментов
- **Целевая сумма** = половина суммы всех элементов (обеспечивает наихудший случай для DP)

## Анализ результатов экспериментов

### Зависимость времени от размера данных

При росте размера входных данных наблюдается следующая картина:

1. **ArrayDP** — время растёт как O(n × targetSum). Поскольку targetSum пропорционален n × avg(value), итоговая сложность примерно O(n²×avg). На практике наблюдается близкий к квадратичному рост.

2. **HashMapDP** — время растёт как O(n × |reachable sums|). Количество достижимых сумм растёт быстрее для разреженных данных, поэтому HashMapDP проигрывает ArrayDP на плотных данных, но может выигрывать, когда targetSum мал относительно количества достижимых сумм.

### Влияние плотности данных

- **Плотные данные** (LOAD_DENSE_1000, диапазон [1, 100]): ArrayDP значительно быстрее, т.к. targetSum мал (~25000), а DP-таблица компактна. HashMapDP создаёт много объектов HashMap, что увеличивает накладные расходы GC.

- **Разреженные данные** (LOAD_SPARSE_1000, диапазон [1, 10000]): Разница менее выражена. ArrayDP создаёт огромную таблицу (n × targetSum), большая часть которой не используется. HashMapDP хранит только достижимые суммы, что эффективнее по памяти.

### Сравнение ArrayDP и HashMapDP

| Критерий | ArrayDP | HashMapDP |
|---|---|---|
| Временная сложность | O(n × target) | O(n × \|reachable\|) |
| Пространственная сложность | O(n × target) | O(\|reachable\|) |
| Поддержка отрицательных | Нет | Да |
| Скорость (плотные данные) | Быстрее в 2-3x | Медленнее |
| Скорость (разреженные данные) | Сопоставимо | Сопоставимо |
| Память (большой target) | Высокая | Умеренная |
| Предсказуемость | Детерминированная | Зависит от данных |

## Заключение

### Соответствие теоретической оценки экспериментам

Теоретическая оценка сложности в худшем случае:
- **ArrayDP**: O(n × targetSum) — подтверждается экспериментами. Время растёт линейно при фиксированном targetSum и линейно при фиксированном n.
- **HashMapDP**: O(n × |reachable sums|) — подтверждается. На плотных данных (малый диапазон) |reachable sums| ограничен, и алгоритм работает сопоставимо с ArrayDP. На разреженных данных |reachable sums| может расти экспоненциально, ограничиваясь лишь общим количеством возможных сумм.

### Выводы из сравнения распределений

ArrayDP стабильно быстрее HashMapDP в 1.5-3x на неотрицательных данных. Это объясняется:
- прямой индексацией массива (O(1)) vs. хеш-таблицы (O(1) амортизированно, но с накладными расходами на хеширование, аллокации и GC);
- последовательным доступом к памяти (cache-friendly) у массива vs. разрозненным у HashMap.

### Сравнение BDD и модульных тестов

| Критерий | Модульные тесты (JUnit) | BDD-тесты (Cucumber) |
|---|---|---|
| Уровень абстракции | Код, методы, классы | Поведение, сценарии |
| Читаемость | Для разработчиков | Для всех заинтересованных сторон |
| Язык | Java | Gherkin (естественный язык) |
| Скорость выполнения | Быстрее (~10 сек на 128 тестов) | Медленнее (~19 сек на 70 сценариев) |
| Гранулярность | Отдельные методы и ветви | Бизнес-сценарии и потоки |
| Документирование | Косвенное (код как документация) | Явное (feature-файлы) |
| Поддержка мокирования | Полная (Mockito) | Ограниченная |
| Параметризация | @CsvSource, @MethodSource | Scenario Outline, DataTable |
| Быстродействие фреймворка | Минимальные накладные расходы | Парсинг Gherkin, маппинг шагов |
| Применимость | Техническая корректность | Бизнес-валидация |

**Вывод**: BDD-тесты дополняют, а не заменяют модульные тесты. Модульные тесты обеспечивают глубокую техническую проверку (ветвления, граничные условия, моки), а BDD-тесты — валидацию на уровне бизнес-сценариев. Быстродействие BDD-тестов ниже из-за дополнительного слоя абстракции (парсинг Gherkin, regex-маппинг шагов), но это оправдано улучшенной читаемостью и документируемостью.
